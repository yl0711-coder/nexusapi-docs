**ホワイトリストを設定すると、登録したIPからだけこのキーを利用できます。空欄ならIP制限なしです。どちらの場合も正しいキーは必要です。**

判定にはプラットフォームが認識した送信元IPを使います。プロキシやネットワークの変更で認識結果が変わることがあるため、キー自体も適切に保管してください。

固定の公開IPを持つPCやサーバー向けです。ネットワークをよく切り替える場合や動的IPの場合は、保存後に使えなくならないよう、送信元IPが固定か先に確認してください。

## 1. 入力するIPを確認する

入力するのは、**NexusAPIへ実際にリクエストを送る環境の公開送信元IP**です。NexusAPIサイトのIPやPCのローカルIPではありません。

| キーを使う場所 | 入力するIP |
| --- | --- |
| PC上のClaude Code、Codexなど | そのPCがインターネットへ接続するときの公開IP |
| 会社のサーバー、自社アプリ、コンテナ | サーバーの実際の送信元IP。管理者に確認 |
| プロキシ、VPN、外部クラウドツール | リクエストを転送する側のIP。PCのIPとは限らないため提供元に確認 |

`192.168.x.x`、`10.x.x.x`、`127.0.0.1`、ドメイン、URL、ポート番号は入力しないでください。

**公開IPが不明な場合：** アプリが動作するPCまたはサーバーで、アプリと同じネットワーク・プロキシ設定を使って確認します。

WindowsではPowerShellを開いて実行します。

```powershell
curl.exe -4 https://api.ipify.org
```

macOS / Linuxではターミナルを開いて実行します。

```bash
curl -4 https://api.ipify.org
```

表示されたアドレスは、この確認リクエストの公開IPv4です。[ipify](https://www.ipify.org/)は外部の公開IP確認サービスです。APIキーは不要であり、送信しないでください。確認できない場合は管理者や回線提供元に問い合わせてください。

アプリだけが別のプロキシを使う場合、クラウド上で動く場合、IPv6で接続する場合は、このIPv4とアプリの送信元が異なることがあります。実際の送信元を確認してから登録してください。

## 2. ホワイトリストを開いて保存する

1. [APIキー](https://nexusapi.link/keys)を開き、アプリが使っているキーを探す。
2. その行の編集ボタンを押す。
3. 「詳細設定」を開き、「IP ホワイトリスト（CIDR対応）」を探す。
4. 実際の公開IPを**1行に1つ**入力する。
5. 「変更を保存」を押す。

新規作成時も同じ欄で設定できます。キーの再コピーや交換は不要です。共有するすべてのアプリや利用者に影響するため、保存前に確認してください。

## 3. 1つ、または複数のIPを入力する

**1つだけ許可する場合：**

```text
203.0.113.10
```

**複数の場合はIPごとに改行します。カンマ、セミコロン、空白では区切りません。**

```text
203.0.113.10
198.51.100.20
```

これらは説明用のアドレスです。そのまま使わず、実際の公開IPに置き換えてください。`https://`、`:443`、`*`は付けません。

## 4. CIDR形式を設定する

### CIDRとは

**CIDRは1つのIPまたは範囲全体を1行で表す形式です：`IPアドレス/プレフィックス長`。** 例は `203.0.113.0/24` です。

スラッシュ後の数値は範囲の大きさを決めます。**ポート番号でも、許可するIPの個数でもありません。**`/24` は24個という意味ではありません。同じアドレス種別では、数値が小さいほど許可範囲が広くなります。

固定の送信元IPを持つPCやサーバー1台なら、公開IPをそのまま入力すれば十分です。CIDRは会社から範囲を明確に指定された場合に使ってください。

### 記入例と実際の範囲

| 記入例 | 許可される範囲 |
| --- | --- |
| `203.0.113.10` または `203.0.113.10/32` | `203.0.113.10` のみ。IPv4アドレス1個 |
| `203.0.113.0/28` | `203.0.113.0` から `203.0.113.15` まで。IPv4アドレス16個 |
| `203.0.113.0/24` | `203.0.113.0` から `203.0.113.255` まで。IPv4アドレス256個 |
| `2001:db8::10` または `2001:db8::10/128` | このIPv6アドレス1個のみ |

説明用のアドレスなので、そのまま使わないでください。自分のIPに安易に `/24` を付けると、単一アドレスから範囲全体へ許可を広げてしまいます。

### 入力欄での設定例

会社が範囲全体と別のサーバー1台を承認した場合は、IPホワイトリストに2行で入力します。

```text
203.0.113.0/24
198.51.100.20/32
```

管理者が確認した実際の範囲とIPに置き換えて保存してください。通常のIPとCIDRは混在できます。**1行に1件入力し、どれか1件に一致すればIPチェックを通過します。** キー、モデル、クォータの他の制限は引き続き適用されます。

飛び飛びのIPが数個あるだけなら、別々の行に入力します。`203.0.113.*`、`203.0.113.10-203.0.113.20`、単独の `/24` は使えません。範囲をCIDRに変換できない場合は、勝手に広げず管理者に正確な値を確認してください。

IPv4とIPv6は混在できます。IPv4の許可だけではIPv6は許可されません。IPv6対応ネットワークで確認するには `curl -6 https://api6.ipify.org` を使います。Windowsでは `curl.exe` を使います。確認に失敗しても、アプリがIPv4を使っているとは断定できません。

**エラーを消すために `0.0.0.0/0` や `::/0` を入力しないでください。** それぞれすべてのIPv4、IPv6を許可し、送信元制限の意味がなくなります。範囲が不明なら管理者に確認してください。

## 5. 保存後の確認とエラー対処

元のアプリから短いリクエストを1回送ります。正常に返れば、そのリクエストはIPチェックを通過しています。他の送信元まで検証できたわけではありません。モデルのテストも通常どおり課金されます。

IPが許可リストにないというエラー、またはIP制限を明示する `403` が出た場合は、次を確認します。

1. アプリが実際に使うキーを編集し、「変更を保存」を押したか。
2. IPごとに改行し、URL、ポート、余計な文字が入っていないか。
3. Wi-Fi、テザリング、プロキシ、サーバーの出口変更で公開IPが変わっていないか。
4. アプリがIPv6や外部サーバー経由で送信していないか。

解決しなければ、アプリ名、発生時刻、キーの名前、エラー原文をサポートへ送り、そのリクエストで認識された送信元IPの確認を依頼してください。キー全文は送らないでください。すべての `403` がIP制限とは限りません。他の原因は[よくあるエラー](/ja/faq/common-errors)を確認してください。

## 6. 制限の変更・解除

同じキーの編集画面で、追加するIPは新しい行に、変更するIPは元の行に入力して保存します。

解除する場合はホワイトリストの**全内容**を削除して保存します。送信元IPの制限はなくなりますが、正しいキーは引き続き必要です。会社が制限を義務付けている場合は、管理者の承認を得てから解除してください。

ホワイトリストだけでキーを保護することはできません。漏えいした場合は制限の変更だけで済ませず、[古いキーを直ちに無効化](/ja/guide/api-key)してください。
